# iCinema 安全与功能问题修复报告

本次修复基于代码检查中确认的问题。图片、表情贴纸继续作为公开资源，允许跨用户访问、引用和收藏；不实施图片内容校验，不引入 Pillow。

结果：`fixed`（本次确认并授权修复的范围）。修改已写入工作区。

## 问题原因与解决方案

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| 上传没有大小限制和存储配额 | 完整读取上传文件；保存前没有限额校验，图片转贴纸也能增加磁盘占用 | multipart 解析前按实际字节限制请求体；单文件分块读取并限制大小；新增用户配额，覆盖头像、图片、贴纸、反馈截图和图片转贴纸。SQLite 写事务串行化配额检查与保存；事务失败清理新增文件。 |
| 修改密码后旧令牌仍有效 | 令牌仅绑定用户 ID，没有可撤销的凭据状态 | 新增 `users.token_version`，改密时原子递增；签发令牌绑定版本，HTTP、刷新接口和 WebSocket 验证版本。已连接的 WS 在处理输入和发送事件前检查版本，撤销后关闭。个人资料页先保存头像，改密成功后重新登录。 |
| 同步播放跳回旧位置 | 快照记录上次操作的位置，前端忽略此后经过的时间 | 播放命令以服务端时间作为锚点；WS 响应携带服务端时间，浏览器使用单调时钟补算播放进度及倍速。加载视频期间暂存的状态，在实际应用时重新计算。暂停状态不累加时间。 |
| 令牌过期后 WS 无法自动重连 | WS 仅重试旧 access token，没有刷新流程 | HTTP 和 WS 共享一次性刷新请求；WS 鉴权失败后刷新并重试一次。刷新令牌无效时退出登录，暂时网络错误继续重试。 |
| 过期图片被访问后漏删文件 | 惰性过期设为 `expired`，后台却只查询 `active` | 清理同时覆盖到期的 `active` 和已标记 `expired` 的图片；文件删除后标记 `deleted`，释放配额并避免反复扫描。清理与图片复用/复制通过数据库写事务协调。 |
| 相同图片重新上传成功但访问 404 | 哈希去重命中了文件已被清理的历史记录，只修改数据库状态 | 仅复用有效且文件存在的图片；其余情况重新保存文件并创建资源记录。 |
| 表情库不传分页参数时报 500 | `page/page_size` 为 `None`，直接参加算术计算 | 分页模式默认第 1 页、每页 20 条；保留 `all=true` 与显式分页参数不能混用的校验。 |
| 切换账户后残留上个账户收藏 | 只清理认证信息，未清内存及用户持久缓存；其他标签页仍保留旧身份 | 登录/退出时统一重置用户 Pinia 状态和旧持久缓存，并断开 WS。请求和令牌刷新记录会话代次，旧会话结果不能写入新会话。通过 storage 事件通知其他标签页清理状态并重新加载身份及页面表单；正常令牌刷新不触发重载。 |

## 配置与上线说明

新增可通过环境变量配置的限制：

| 环境变量 | 默认值 |
| --- | --- |
| `MAX_REQUEST_BYTES` | 67,108,864（64 MiB，包含 multipart 开销，兼容一次提交多张反馈截图） |
| `MAX_UPLOAD_BYTES` | 10,485,760（单文件 10 MiB） |
| `USER_MEDIA_QUOTA_BYTES` | 1,073,741,824（每用户 1 GiB） |

配额按用户创建、尚未完成物理清理的资源记录计费；复用已有公共资源不会重复计费。历史孤儿文件和进程异常退出遗留文件不在数据库配额统计内，仍需要运维回收。

新增 Alembic 迁移 `b19f06a8c321`。沿用项目启动时自动迁移机制；本次没有修改现有业务数据库。升级后，旧令牌视为版本 0，在用户第一次改密时失效。前后端应一起更新；改密后需要重新登录。

过期图片物理清理仍由独立的 `python -m jobs.starter` 进程执行。此次修复没有改变它的启动方式。

主要变更位置：后端 `app/core/body_limit.py`、`app/modules/media/{storage,repository,service}.py`、认证及用户模块、`app/realtime/` 和上述迁移文件；前端 `src/infra/auth/`、HTTP/WS 客户端、播放状态及播放器、个人资料页和认证 store。验证代码位于上述前后端测试文件。

验证边界：未连接生产环境、未做多人真实浏览器端到端测试或资源耗尽压力测试。同步补偿消除了历史位置和设备时钟差异问题，但仍可能有网络单程延迟造成的小幅误差。
