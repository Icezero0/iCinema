# iCinema 资源库、Omofun 与房间选片设计

日期：2026-09-22，修订版 v6.4。本文统一替代此前总体计划；阶段进度与验收见[分阶段实施与本地验收](cms-implementation-stages.md)。恢复资源库方向，优先评估“独立现成 CMS 管理资源，iCinema 调用接口”的方案，见第3.4节；独立CMS已部署，采集和接口验证进行中。采集范围已扩大为各类影视资源，不再限于日本动画。自研4A–4D保留作备选，暂不实施其数据库扩展。Omofun 已有解析缓存及房间接入，保留其专项回归待办，不以本次恢复资源库视为完成 O3。

## 1. 目标与已确认决策

同时建设两条资源获取路径：

| 路径 | 数据从哪里来 | 何时获取 | 用户如何使用 |
| --- | --- | --- | --- |
| 资源库 | 多个资源采集站聚合；优先验证由独立 CMS 管理 | CMS首次全量、之后定时增量；iCinema按需查询 | 在本站搜索作品、选择剧集和线路 |
| Omofun | 用户提供的 Omofun 作品 ID 或网址 | 首次解析、缓存超过24小时或用户主动刷新 | 输入作品，选择解析出的剧集和线路 |

两条路径共用房间选集、选线与同步播放能力，但不混用作品管理流程。Omofun 解析结果保存到独立缓存表，不自动成为资源库作品，也不要求管理员逐部建档。

房间提供“视频链接”“本地视频”“资源库”“Omofun”四种模式。**缓存刷新和后台同步都不得自动打断正在播放的房间。** 新数据供下一次明确选集、换线或重新加载使用。

2026-09-22用户确认采集范围扩大为各类影视资源，包含电影、电视剧、动漫、综艺等，不再限制日本动画、地区或年份。分类及各站分类绑定由管理员在CMS配置；iCinema动态读取CMS分类，不内置封闭的分类清单。既有自研库仅预置“日本动画”，属于历史初始数据；其默认值和单分类映射限制仍是实现现状，见下文核查。金鹰是首个采集站实例，不是写死的唯一来源。线路数量由每集实际聚合结果决定。暂不建设未来正版资源站协议、权益体系、DRM、全站 Omofun 爬虫或自动换线。

验证依据：

- [金鹰接入评估](jinying-provider-assessment.md)与[增量参数评估](../reports/jinying-incremental-assessment.md)：已取得作品、剧集及 M3U8；后续验证了分类、相对更新时间窗口、分页、批量详情和分页详情。
- [Omofun 验证](../reports/omofun-link-feasibility.md)：公开详情页提供选集，页面调用的 JSON 提供每集线路。属于网站内部接口，不等于稳定的采集协议。

### 2.1 2026-09-22 代码核查：目标与实现的差距

| 目标 | 现有实现与差距 | 下一步 |
| --- | --- | --- |
| 多采集站聚合 | `discovery_service.py` 会遍历同分类的已启用实例；已有跨站合并、补集和幂等更新。真实站点只验证过金鹰，其他实例是模拟测试；目前按完整名称和无冲突元数据匹配，尚无完整人工合并/拆分 | 保留现有作品/集/线路模型；增加独立站点能力配置、映射及冲突处理，逐站验证兼容性 |
| 首次全量入库 | 检索每次重新分页 `ac=list&t&pg`，本地按名称/日期筛选，命中后逐部 `ac=detail&ids`；未使用 `h`、`pagesize`、批量详情 | 新建持久来源目录，按配置范围分批全量取得元数据与播放链接，支持暂停恢复 |
| 可复用的采集目录 | `CatalogSource` 要求绑定本站作品，记录的是导入基准快照；未导入候选仅在任务 JSON 中，没有可独立检索的来源目录 | 将“来源最新数据”与“正式作品/上次已应用快照”分开，不必先建本站作品才能保存采集记录 |
| 每日增量 | 没有采集计划、成功覆盖时间或增量窗口；`jobs/starter.py` 只注册图片清理 | 每站每分类独立同步范围，持久化日程、水位、任务和恢复状态 |
| 长时间可靠执行 | 有限重试、取消和租约已有；执行依赖 FastAPI `BackgroundTasks`。租约过期仅标记中断；检索重试从第一站第一页开始 | 独立 jobs 执行器扫描到期计划及待执行任务，按来源范围认领并恢复，不依赖某次浏览器请求 |
| 大规模检索 | 候选连同剧集地址存在单个任务 JSON；每加入候选会复制列表、读取同分类作品。单站1000页、候选5000条是保护上限 | 使用逐条来源记录、索引与分页查询，避免把放大上限当成全量方案 |
| 自动补线路 | `sync_work` 已支持指定本站作品新增来源、补集、更新链接及保护手工值，但当前由管理员选择导入触发 | 同步后自动应用已有绑定；新站记录唯一可靠匹配已有作品时自动补线，冲突留待处理 |

上述金鹰详情与增量结果来自既有实测。2026-09-22已额外验证金鹰、iKun、非凡、丫丫四站列表接口返回JSON和分类，具体历史URL见第3.4节；这不能代替CMS内采集、跨站合并或增量验证，也不能代表后来选定的五站接口已验证通过。

### 2.2 分类必须从数据和配置中获得

现有 `CatalogCategory` 表、分类读取接口和三个管理页的下拉框已经支持动态分类；类别校验读取数据库，地区也没有限制为日本。但“可以手动往数据库加分类”还不等于完整的分类管理能力：

- `models.py` 和 `schemas.py` 仍默认 `japanese_animation`，漏传分类会静默归入日本动画。应要求明确选择有效分类，不设固定代码默认值。
- 分类接口仅有 GET，没有新增、改名、排序、停用操作。补齐管理入口；分类标识稳定，改名不改变既有作品身份；被引用分类优先停用而非直接删除。
- `CatalogProvider.category/upstream_category` 是一对字段，一个站只能对应一个分类。应拆为一站多条映射；同站多个上游分类可以对应同一本地分类，同一上游分类不能同时映射到多个启用的本地分类。不要求为了多采一个分类重复添加同一站。
- `import_parser.py` 把所有作品写成 `content_type="tv"`。应根据可确认的上游信息或映射配置确定内容形式，无法确定时保留“未知”；电影、剧集、综艺、纪录片等不能因采集器默认值而被误判。分类、地区、内容形式各自独立，作品归类仍由映射决定。
- 前端空结果提示及后端连接检查仍含固定的“日本动画”措辞，改为通用文案。分类显示名由数据提供，允许中英文名称；现有按 code 优先使用固定翻译的写法不能遮蔽管理员对内置分类的改名。
- 历史迁移中的日本动画、金鹰分类25和播放组是初始化数据，保留兼容；后续分类管理不再需要改源码或发迁移。不要通过修改历史迁移改变已部署数据库。

建议关系：`采集站 → 多条上游分类映射 → 本站分类`。例如同一站的“日本动漫”“国产动漫”“动作片”，可分别配置为本站的“日本动画”“国产动画”“电影”；示例名称和上游 ID 均由实际接口及管理员配置决定。

## 3. 资源库路径：先同步，再检索与导入

以下3.1–3.3记录自研方案及其可靠性要求；用户补充独立 CMS 思路后，优先验证3.4的分工方案。两个方案是替代关系，不同时建设两套资源管理后台。

自研目标流程：

采集站配置 → 同步来源目录与详情 → 管理员本地筛选、预览 → 选择导入或更新 → 发布作品 → 房间使用。

### 3.1 将来源目录与正式作品分开

新增独立来源目录记录，以“采集站实例 + 上游作品 ID”唯一标识，保存名称、分类、更新时间、规范化详情、原始必要字段、详情获取时间及同步批次。未导入的条目也保留，避免每次检索重复抓取。

管理员依旧按名称、分类、更新日期筛选所有符合条件的已启用采集站，不要求先选择某一个站。每项显示来源站数、集数、预计新增集数和已建档状态；聚合不确定时保留独立候选与必要警告。目录尚未完整同步时必须标明覆盖状态。

已有作品可以再次导入，用于补充新集、更新地址或增加新站线路。定时同步自动应用已有绑定；新增站点提供的记录即使尚未绑定，只要唯一、可靠匹配到已有作品，也应能自动绑定并补线。匹配不明确、元数据冲突或被管理员禁止合并时保留待处理，不猜测归属。新作品进入候选目录，管理员可选择或按筛选结果批量建草稿，不自动发布；同步必须保护人工修改、映射及禁用状态。

“首次全量”是将各站**已启用分类映射范围内**的作品、剧集及链接完整存入来源目录；不自动扩大到全站所有分类，也不等于将全部条目自动发布。首次全量按同步范围分别完成：新增站点或新分类只补该部分的基线，已有范围继续增量。它也不排斥后续低频完整对账。

第一轮同步可先取得列表，再分批取得详情。没有详情的条目不能宣称已知完整线路数量；统计完成后才作为完整预览。批量导入应明确作用于当前选择或全部筛选结果。

### 3.2 金鹰参数与增量策略

已验证可用参数包括：

| 参数 | 用途 |
| --- | --- |
| `ac=list` / `ac=detail` | 列表 / 含播放数据的详情 |
| `t` | 上游分类 ID，由配置映射本地分类 |
| `pg`、`pagesize` | 分页；页大小按站能力和响应大小上限设置 |
| `h` | 最近若干小时内更新的条目 |
| `ids` | 按作品 ID 批量取得详情 |

金鹰帮助页说明搜索关闭，不能依赖 `wd` 实现名称查询。名称筛选改在本站来源目录进行；绝对日期范围由本站过滤，增量请求使用上游支持的相对小时窗口。其他站是否支持这些参数，须逐实例验证。

首次按配置分类完成全量同步，之后每天在可配置时间运行增量任务，明确调度时区，并分别配置上游无时区时间的解释规则。每个“采集站 + 分类映射 + 采集配置版本”保存独立水位，含义是已完成同步的覆盖时间：

1. 记录本次任务开始时间，固定下界为上次成功水位减去重叠窗口；每次请求按当前时间距此下界的时长向上取整计算 `h`，避免长任务中的相对窗口向前滑动而丢失早期记录。
2. 分页取得更新记录；优先使用已验证的详情分页或受响应大小约束的批量详情，减少逐部请求。
3. 分批幂等写入目录，更新已绑定作品，保留新增未导入候选。
4. 只有完整成功后才把水位推进到本次任务开始时间；失败、取消、超限或缺页均不推进。
5. 停机后按实际遗漏时间补采；新增采集站或改变分类、接口等采集范围配置执行对应基线同步。仅改展示名称、缩写或每日执行时间不使目录失效；区分编辑版本与影响数据范围的版本。
6. 周期性完整对账补偿回填旧时间、分页变动等增量遗漏；上游缺项不直接删除或下架本站内容。

实测列表按更新时间倒序，但没有稳定快照或同时间排序保证。重叠、去重和对账均有必要。“每天运行”不等于每次固定请求最近24小时；停机数天也不能只补一天。

接口能力按站点记录：是否支持分类、相对小时、分页详情、批量ID、页大小及可用播放组。当前协议实现仅覆盖这类 JSON 采集接口；不支持 `h` 的站采用低频全量核对，不能把参数被忽略的结果标成增量成功。已有 HTTPS、公网地址和重定向限制继续保留；新站如有协议差异应增加明确适配，不能直接放宽地址校验。

### 3.3 调度与可靠性

沿用现有 `python -m jobs.starter` 进程承载同步执行器，现有间隔循环只负责唤醒；每日时间、时区、下次到期和运行历史保存在数据库中。新增持久任务、游标、执行租约和条目结果；当前进程内检索任务不能直接当作可靠定时系统。实施阶段提供 jobs 的运行说明，由用户启动，开发者不启动任何本地服务。

每站限速、有限并发和退避，网络请求不占数据库长事务。取消保留已提交结果；恢复从安全检查点继续，并允许重复处理。详情解析失败保留最后成功数据与错误，不能用空结果覆盖完整记录。管理端显示同步覆盖范围、最后成功时间和任务进度。

任务按站点和分类拆分，一站失败不阻止其他站成功推进；同一同步范围不能被手动任务和定时任务重复认领。现有跨站任务只以第一个站点作为活跃任务唯一键，不能直接用作所有来源的同步锁。陈旧 worker 的写入和完成操作都必须校验租约及采集配置版本。分页位置仅作任务内检查点，上游列表变化时允许回退重扫，不能当作长期水位。

来源目录更新与向正式作品应用的结果分别记录：待人工匹配不是网络失败，不能因此不断全量重采；抓取、解析失败不能伪装成完整覆盖。若作品更新发生版本冲突或失败，保留独立待应用记录，后续重试不依赖上游再次更新。管理员删除作品后保留抑制自动重建的决定，后台任务不能把刚删除的作品重新建回；重新导入由管理员明确触发。

首版不默认引入 Redis、Celery 或第二套数据库；确需依赖时先说明用途和安装命令。

### 3.4 优先评估：独立苹果 CMS，iCinema 消费资源接口

用户提供的[部署教程](https://linux.do/t/topic/68339)发布于2024年，使用苹果 CMS v10，并搭配前台主题、播放器配置和定时触发。这里只借鉴 CMS 管理与应用分离，不照搬其旧版本和全部插件。2026-09-22已由用户在Ubuntu VPS部署固定版本 `v2026.1000.4056`，并通过SSH隧道登录后台；CMS内采集、定时任务及iCinema运行联调仍待验证。部署及兼容补丁状态见[阶段计划](cms-implementation-stages.md)。

推荐分工：

| 独立 CMS | iCinema |
| --- | --- |
| 配置多个采集站、分类及分类绑定 | 向后端请求资源列表、分类和搜索 |
| 首次全量、日常定时采集及失败补采 | 读取 CMS 作品详情并转换为统一选集/线路结构 |
| 作品去重、播放组更新、内容编辑和上下架 | 展示简介、封面、集号、线路和自定义缩写 |
| 作为资源元数据的唯一维护端 | 保存必要缓存和房间当前播放快照，负责权限及同步播放 |

数据流：`多个采集站 → 独立 CMS及其数据库 → iCinema后端适配接口 → 房间选集与同步播放`。iCinema 首版无需再全量复制一个可编辑资源库，也不直接读写 CMS 的数据库；新增分类和调整采集范围在 CMS 操作。

**源码已支持的基础**：项目本身使用 PHP+MySQL；后台提供分类管理和采集分类绑定。可复用管理端，iCinema不需要其影视前台主题。播放组标识仍需要在 CMS 正确配置，否则可能被采集过滤，不等于需要安装第三方播放网页脚本。[项目说明](https://github.com/magicblack/maccms10)、[分类管理](https://github.com/magicblack/maccms10/blob/master/application/admin/controller/Type.php)、[采集绑定](https://github.com/magicblack/maccms10/blob/master/application/admin/controller/Collect.php)。

**查询接口**：可通过 `api.php/provide/vod/` 使用 `ac=list`、`wd`、`t`、`pg` 查询，`ac=detail&ids=...` 获取详情；列表附带分类，详情包含 `vod_play_from` 和 `vod_play_url`。这是自建 CMS 查询自己的数据库，名称搜索不依赖金鹰是否开放搜索。接口需在部署中启用和配置；多播放组返回分隔符、分页、上下架过滤及缓存必须做契约测试，不能原样复用当前只选择单播放组的导入器。[Provide接口源码](https://github.com/magicblack/maccms10/blob/master/application/api/controller/Provide.php)。

**合并边界**：采集器可按名称、分类、年份、地区等配置匹配，并增加新播放组或更新已有组；这不是语义理解或相似度保证。同名不同作品、不同季、别名以及两个采集站使用相同播放组标识，都需样本验收，必要时配置独立组名/人工修正。其作品锁定也不能直接视为本站逐字段保护。[采集模型源码](https://github.com/magicblack/maccms10/blob/master/application/common/model/Collect.php)。

**定时边界**：现有定时入口会在调用采集前写运行时间，因此该时间不能当作“完整成功水位”。应使用系统定时器触发正确任务入口，验证多页完成、超时重试与漏跑补采。固定最近24小时在停机后仍会漏数据；必要时在 CMS 侧加一个小型任务包装器记录成功范围、扩大窗口及低频核对，而不在 iCinema 重建采集系统。[定时入口源码](https://github.com/magicblack/maccms10/blob/master/application/api/controller/Timming.php)。

**手动全量边界**：后台“采全部”通过浏览器JavaScript翻页继续采集，执行期间需保持页面和SSH隧道连接；不等于关闭页面后仍会完整执行的后台任务。当前采集器共用断点记录，首轮按站串行，不同时启动五站采集。定时入口与浏览器采集的执行路径不同，仍须单独验收自动翻页、超时和恢复。

**iCinema仍需实现的适配**：

1. 后端只访问管理员配置的 CMS 地址，用户只能提交关键词、分类ID和作品ID；统一权限、超时、分页和返回校验。自托管 CMS 如在局域网/容器网内，使用单独的受信地址配置，不放宽现有公共采集站 URL 校验。
2. 分类以 CMS 的ID、名称及父级数据动态显示，可选配置显示别名/语言；不默认日本动画，也不沿用分类25或强制TV。CMS类型与本站内容形式不能不加区分地互相代替。
3. 全部有效播放组转换为“集号合集 → 每集可用线路”；保留原始集名和线路标识。集号不能简单按各线路数组下标对齐；总集篇、缺集、电影与日期集名需适配。线路显示名/缩写与内部标识分开，不将站数当作必然的线路数。
4. 只持久化 CMS实例+作品ID、必要的短期详情缓存和房间已选播放快照；CMS 刷新不自动切源。CMS故障时已选房间仍使用快照，新查询明确失败或使用标明时效的已有缓存。
5. 后端读取并清理 CMS 文本，校验播放地址；不用 iframe 嵌入其播放器，继续复用本站 HLS 引擎。上线前验证被禁用/下架作品不会通过对外接口进入新选片，缓存不会长期绕过状态变化。

**与既有成果的关系**：作品/集/线路思想、集名解析、共通选集界面、权限和房间播放快照可复用；现有资源管理、采集任务、`CatalogSource` 绑定先保留，不立即删除、迁移或双向写入。外部方案通过验收后再决定旧库迁移、管理页改入口及停用自研采集模块，避免两套数据互相覆盖。Omofun 保持独立路径。

## 4. 作品、剧集与线路模型

以下为既有及自研备选模型。外部 CMS 方案保持同样的选集语义，但不要求将整套管理数据再次复制到这些表；现有表先保留：

- `CatalogContent`：本站作品，含分类、名称、年份、地区、形式、发布和禁用状态。
- `CatalogEpisode`：作品内所有来源集号的合集，结合篇目类型区分；不是每个采集站各建一套集数。
- `CatalogLine`：作品下来源实例及播放组对应的线路。
- `CatalogPlayback`：某集、某线路对应的具体地址；没有该集的来源不生成空播放项。
- `CatalogProvider`：资源采集站实例；展示优先缩写，未填则用名称，不自动追加 M3U8。分类映射拆到独立关系，避免把站点等同于某一种资源。
- `CatalogSource`：已导入的来源作品与本站作品绑定及导入快照。
- `CatalogImportJob`：现有检索和导入任务，不能替代独立来源目录或增量水位。

新增分类映射、来源目录、同步范围/水位、计划及逐项任务记录，具体表名在实现阶段确定。来源目录允许未绑定作品；保持“站点 + 上游作品ID”唯一，不因作品换分类生成重复记录。归属关系继续以 `CatalogSource` 为唯一依据，目录不再存另一份可独立修改的作品绑定。

来源目录存最新上游快照，`CatalogSource.snapshot` 仍存上次应用到正式作品的基准；不能直接以新抓取数据覆盖这个基准，否则人工字段保护会失效。保留已有 provider/content/episode/line/playback ID，将每站现有分类对迁为一条映射；已有绑定只能回填为部分来源记录，不能声称因此完成全量覆盖。迁移在隔离数据库验证数量及外键，不重建或清理无关房间数据。

剧集解析先提取有效 HTTP(S) M3U8 地址并保留查询参数，再识别集号；无集号按既定顺序规则兜底。明确集号之间的插入项使用 x.5，多项使用 x.51、x.52 等既有规则，并保存原始标签和顺序。该规则是映射策略，不能证明不同站的总集篇内容一致；冲突须可人工纠正。作品名称中的不同季保留，不新增季字段。

自动聚合沿用完整名称、分类及无冲突的年份、地区、形式等保守条件。暂不把固定评分阈值或模糊名称识别当作已实现功能。已有来源绑定优先复用，重要元数据冲突进入待处理，不静默改绑。

完整人工整理后续提供合并预览、主作品选择、剧集对应、拆分、禁止再次合并及字段锁定。自动同步不覆盖这些决定；操作检查版本并记录审计。合并不能仅依据数组下标对齐不同来源的剧集。

## 5. Omofun 路径：按作品解析与持久缓存

### 5.1 输入与解析

用户输入作品 ID 或已支持的 Omofun 网址。后端提取并规范化作品 ID，再根据固定域名和路径模板访问详情页及每集线路接口；不能直接抓取用户提供的任意 URL。

已验证的解析方式为：读取作品详情中的集标识，再请求 `/_dyn_plays/{作品ID}/{集标识}`，从 `video_plays` 的 `src_site` 和 `play_data` 提取来源及地址。按需支持已验证的页面形式，不执行页面脚本，不渲染上游 HTML，不安装站方播放器。

解析放在后端，前端只访问本站接口；不依赖第三方页面向本站开放跨域读取。首版不提供 Omofun 站内搜索和全站抓取，用户自行搜索后粘贴作品。

一次作品解析取得完整选集及逐集线路。集数较多时用异步任务显示进度，限制并发、请求数、响应大小和总耗时；不能让一个 HTTP 请求无限等待。

### 5.2 缓存结构与24小时规则

建议在现有数据库增加独立缓存表，形成逻辑独立的 Omofun 缓存区，无需新增数据库服务。以下是拟议字段：

| 数据 | 内容 |
| --- | --- |
| 缓存索引 | provider=omofun、字符串作品 ID、当前成功版本 |
| 成功快照 | 作品标题、稳定集标识、排序、线路来源标识及 HLS 地址 |
| 时间 | 最后完整解析成功时间、到期时间 |
| 刷新任务 | 状态、执行租约、开始时间、错误和有限重试信息 |
| 版本 | 单调递增的成功快照版本；旧版本保留或复制到房间播放快照 |

规则：

- 无成功缓存：启动解析，展示进度；成功后返回可选内容。
- 距最后成功解析不足24小时：直接返回已有快照。
- 达到24小时或用户主动重新解析：发起刷新；已有快照可继续用于展示，并明确刷新状态。
- 同一作品并发请求合并为一个刷新任务；主动刷新也受限频约束，不无限创建任务。
- 完整成功后原子替换当前缓存版本；失败或部分解析失败保留旧版本，记录错误，不延长其成功时间。
- 首次解析不完整时不标记完整成功，也不把部分结果伪装为完整选集。
- 24小时表示目录刷新周期，不保证 HLS 地址24小时有效。失效时提供重新解析及显式重新加载、换线操作。

Omofun 的来源标识不自动等于已配置采集站实例。同一来源可能贡献多个地址；同一集完全相同地址可以去重，但不同地址保留。不删除签名参数去重，不以返回数组下标作为长期线路 ID。优先利用稳定上游标识；无法可靠对应时产生新线路标识并保留旧房间快照。

## 6. 四种房间模式与播放快照

| 用户名称 | 内部类型 | 持久选择信息 |
| --- | --- | --- |
| 视频链接 | `external_url` | 当前外链及必要格式信息 |
| 本地视频 | `local_file` | 现有文件识别信息，不保存或广播本机路径 |
| 资源库 | `catalog` | 作品、剧集、线路/播放项 ID |
| Omofun | `omofun` | 作品 ID、稳定集标识、线路标识、所用缓存版本 |

模式、选择引用与当前播放描述分开。房间保存模式及选择；服务端在明确切源时生成房间播放快照，包含实际地址、格式、剧集、线路、数据版本及递增的 `source_revision`。

### 6.1 刷新不打断播放

缓存成功从版本 A 更新到 B 时：

1. 缓存默认指针指向 B，选集面板可以显示新剧集、新线路。
2. 正在播放 A 的房间继续使用自己的 A 播放快照，不广播切源，不替换 video.src，不暂停、不重置进度。
3. 新加入或重连的成员取得房间当前快照 A，不自行按作品 ID 解析成 B。
4. 有切源权限的成员明确选集、换线或重新加载后，房间才选择 B 的具体播放项并广播新的源版本。
5. 删除过期共享缓存不能让仍被使用的快照失效；房间持有必要播放描述，旧版本回收考虑引用生命周期。

“重新解析”只刷新候选数据，“重新加载当前线路”才改变房间播放源。即使刷新由该房间成员发起，也不把两项操作自动串联。当前线路在新快照中消失时保留正在播放的快照，下一次选择提示重新选线，不按下标替换。

该保证同样适用于资源库后台同步和普通元数据更新。管理员明确禁用、删除或下架的处理属于权限和可用性控制，应单独通知受影响房间停止使用，不能把普通刷新当作此类操作。

### 6.2 权限与同步

切模式、切集、切线和重新加载复用现有房间成员及主动同步权限；读取缓存不能赋予修改房间的权限。后台 CMS 操作仍仅管理员可用。

所有异步选片结果和播放事件检查房间源版本，用户已切模式时丢弃迟到结果。普通缓存更新不递增房间源版本；真正选择变化才原子递增并广播。

切集默认暂停并从头开始。跨线路时间轴尚未验证，不能因为集号相同就承诺无差别续播；首版手动换线，可明确选择尝试保留进度，但需允许人工校准。第一版不做每人独立换线或自动连播。

复用既有媒体引擎，播放描述显式携带 HLS 格式。上游解析成功与浏览器能否解码、加载分片分开验收；不增加任意视频代理。

服务重启后恢复持久模式与选择，暂停并重新建立播放描述，不承诺恢复重启前的连续播放或精确进度。当前进程内房间状态的部署限制继续保留。

| 用户资源库 | 搜索已发布且未禁用的作品、查看选集 |
| 房间 | 四模式选择；资源库选片，Omofun 输入、刷新及选集选线 |

Omofun播放源面板提供链接/作品ID输入、当前状态和成功作品名、仅解析时显示的进度条、解析按钮和“打开选集”。输入链接提取的ID或直接输入的ID与房间成功解析作品一致时，按钮变为“重新解析”并强制重取（保留冷却限制）；不一致时显示“解析”，优先读24小时内成功缓存。不设置独立刷新按钮。房间以 `omofun_resolution` 保存解析对象和状态，独立于输入草稿及当前播放快照；即使未选择播放线路，重进也恢复解析作品。打开选集只打开当前成功结果，不触发解析，也不受输入框修改影响。弹窗使用共通卡片背景及暗色遮罩，打开后固定本次选集数据与播放源版本。点击线路应用到房间，界面不显示外链。底层映射至既有外链/HLS引擎，后端根据作品/集/线路ID及缓存版本取得地址，客户端不能以Omofun名义提交任意地址。线路名按上游前两位大写加“线路”，不再使用完整来源代码作为按钮文字。

界面继续使用共通组件、主题和中英文 i18n。反馈使用 toast，不在标题下长期占位；不增加开发提示和不必要副标题。选集使用数字按钮；线路优先缩写、否则名称，不额外显示 M3U8 后缀。失败仅显示必要原因和恢复入口。

新增接口按职责划分为来源目录查询/同步任务、用户目录、Omofun 解析任务/缓存读取、房间选择/播放快照；具体路径在相应阶段确定，避免将拟议地址写成现有 API。房间解析按内部标识操作，不能成为匿名通用网页抓取器。

## 8. 数据与请求边界

延续现有公网 HTTPS 请求防护、DNS 校验及绑定、超时、响应大小和限速策略；Omofun 使用固定允许域名并校验所有请求目标。任何新增重定向支持也须逐跳检查。上游内容按不可信数据解析，不执行脚本、不直接渲染 HTML。

缓存写入与房间切源分离，远程请求在数据库事务之外。控制 SQLite 写入批次和保留期限；不全量下载或探测视频。日志不输出完整签名地址、凭据或用户本地路径。

分类、采集站启停、人工覆盖、禁用与删除优先于自动同步。来源缺项、一次超时、播放失败均不直接触发批量删除。资源库发布状态与 Omofun 缓存状态是不同概念，互不代替。
